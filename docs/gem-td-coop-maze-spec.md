# 甜點守衛戰：合作迷宮模式（設計草案）

> 狀態：草案，尚未實作。範圍：**網頁版、電腦版先行**，用來驗證「共用大地圖」好不好玩。
> 手機版、Steam 版、多隊對戰都不在第一版，但設計上要留出口（見第 7 節）。
> 相關文件：`gem-td-spec.md`（現行規則）、`gem-td-steam-plan.md`（Steam 方向）。

## 1. 為什麼要做

現行模式每人一張獨立地圖，只共享血量與波次，本質是「平行單人遊戲」，玩家之間幾乎沒有互動。合作迷宮改成**全隊共用一張大地圖、一起蓋同一條迷宮**，讓「討論分工、互補、互相補洞」成為核心體驗。

要驗證的問題：

1. 多人同時在同一張圖上放置，會不會好玩，還是只會混亂？
2. 允許堵死、由怪物拆牆，是否比「禁止堵死」更有趣？
3. 玩家之間是否真的會溝通與分工？

## 2. 規則

### 2.1 模式與人數

- 新增 `options.mode = 'coop'`（與現有 `'relay'` 並列，大廳選項）。
- 第一版 2～3 人；`config.js` 的 `COOP` 區塊留 4～6 人的尺寸表，但不開放。
- 現有模式一律不動。
- 建造者與施工機制見 2.6；放置與拆除統一成「工作」資料：`job = { type: 'build' | 'demolish', cell, owner, duration, progress }`。`instant` 模式等於 `duration = 0`。

### 2.2 地圖

- 全隊一張，尺寸隨人數放大，由 `coopLayout(playerCount)` **參數化產生**，不手寫死：

| 人數 | 尺寸（暫定）| 路徑點 |
|------|-------------|--------|
| 2 | 35×35 | 8 |
| 3 | 40×40 | 9 |
| 4～6 | 45～55（保留）| 10～12 |

- 起點、終點、路徑點不可放置（沿用現行規則）。
- 第一版只做一張版型（蛇行），`coopLayout` 的簽名要能之後換版型。

### 2.3 回合流程

流程與現行相同（放置 → 選擇 → 準備 → 出怪 → 結算），差別在於**放置階段全隊同時在同一張圖上操作，而且由「建造者角色」親手蓋**（見 2.6）：

- 每人仍各拿 5 顆、各選 1 顆留下，其餘變餅乾牆。
- 放下的寶石**即時**顯示給所有人，用玩家顏色標示擁有者；施工中的格子也看得到。
- **同一格先到先得**，由伺服器判定；後到者收到 `CELL_TAKEN` 錯誤。因為要先走到才能蓋，實際衝突會很少。
- 建造秒數預設提高到 90 秒起（走路加 5 顆 × 3 秒施工），可選 90／120／不限時；實際數字要試玩決定。
- 第一版預設用 `COOP.buildMode = 'builder'`；`'instant'`（點了立刻蓋好、不用走路與施工，加上游標預定標記當軟鎖）保留作比較與除錯用。

### 2.6 建造者與工作

**角色**：每位玩家一個建造者（小烘焙師，素材 `public/gem-td/builder/chef.webp`，玩家色由程式換色）。

- 點地圖移動；第一版**自由移動、不碰撞**，不受餅乾牆、塔阻擋，怪物也不攻擊它。
- 移動速度 `COOP.builderSpeed`（暫定每秒 4 格）。
- 地圖縮小到每格小於 `COOP.builderMinCell` 時，改畫玩家色圓點加名字。

**放置（5 顆寶石）**：

- 畫面下方的手牌區就是這回合那 5 顆寶石。選一顆，再點地圖上的目標格。
- 建造者走到目標格 `COOP.buildRange`（暫定 3 格）內，開始施工，**每顆需要 3 秒**（`COOP.buildSeconds`）。
- 施工開始的那一刻，格子就算障礙物（路線預覽與突破點馬上更新，隊友立刻看到），施工進度條顯示在格子上。
- **一個建造者同一時間只做一件工作。** 施工中再選別的寶石或別的格子，等於取消目前這件（沒有任何損失）。
- 施工完成：寶石正式放在格子上，並歸屬於該玩家。

**取消（返回）**：

- 施工中可隨時取消：寶石**回到手牌**、格子釋放，**不扣金幣、不扣時間以外的任何東西、沒有懲罰**，可以馬上選別的位置重新施工。
- 取消不需要走到現場，點手牌中該顆（或再點一次進度條）就生效。

**拆除**：

- 拆餅乾牆也要時間（`COOP.demolishSeconds`，暫定 3 秒），要走到範圍內才開始。
- 進行中塔／牆還在；取消就什麼都沒發生；完成才移除。
- 現行「拆餅乾牆免費」只是不用花金幣，現在改成要花時間，金幣仍然不收。

**待決定**：已經施工完成、但還沒選「保留哪一顆」的寶石，能不能收回換位置？建議：可以，**選擇保留之前免費且瞬間收回**（這取代現行的復原功能）；一旦按了保留，就變成需要拆除。

### 2.4 經濟與成長

| 項目 | 歸屬 |
|------|------|
| 金幣、品質、研究、匠心加給、許願、重骰 | 各人獨立 |
| 擊殺金幣 | 給**塔的擁有者**（`tower.owner`）|
| 血量 | 全隊共用（`team`）；不開放 `solo` |
| 合成、特殊塔 | 只能用**自己擁有**的塔（沿用「只能使用自己的塔」，配方邏輯不用改）|
| 熟練度 | 跟著塔 |
| 主動技能 | 全隊共用一組，冷卻共用（避免多人疊技能）；誰施放都可以 |

- 怪物血量隨人數加成：`COOP.hpPerPlayer`（暫定每多一人 +80%），因為共用地圖上的總火力與人數成正比。數值要用 `balanceSim.js` 的機器人調，不憑感覺。
- 交換、贈送塔給隊友：**第一版不做**，欄位（`owner`）已留好，以後只是改 owner。

### 2.5 堵死策略（核心設計）

不在放置時驗證路線是否通。原因：多人同時放置時，「這一顆會不會堵死」的檢查在別人同一瞬間也在放的情況下無法可靠判斷。

改成 `config.COOP.blockPolicy`：

| 值 | 行為 |
|----|------|
| `'validate'` | 沿用現行：放置時檢查，會堵死就拒絕（保留給日後比較用）|
| `'breach'` | **coop 預設**：允許堵死，怪物拆牆前進 |

`breach` 的行為：

1. 尋路由 BFS 改為**加權最短路（Dijkstra）**：空地成本 1，餅乾牆成本高，塔更高。
2. 有通路就走通路；沒有就走**成本最低的突破點**，怪物停在該牆前攻擊。
3. 牆有血量（`COOP.wallHp`，隨波數成長），被打破後該格移除、重新尋路，後面的怪直接通過。
4. 建造階段持續顯示**路線預覽**；被堵死時用紅色標出預計的突破點，讓隊友有機會補強。
5. 空軍不受影響（本來就直飛）。
6. 防止「全堵死就贏」：牆血量隨波數成長；怪物停在牆前時是塔最密集的區域也不應該無限安全，由平衡數值處理。
7. 防惡意：建造階段**任何人都能免費拆餅乾牆**（現行是免費，只是限本人），塔不能被別人拆。

**待決定**：突破點若是「塔」而不是餅乾牆，塔要不要有血量、被破壞會怎樣？建議第一版：塔也算牆但成本與血量都遠高於餅乾牆，被破壞時該塔直接消失（擁有者損失）。若玩測後覺得太痛，再改成塔不可被拆、堵死僅限餅乾牆。

## 3. 架構改動

### 3.1 共用棋盤抽象（最重要，也是未來彈性的來源）

現在每個玩家 `p` 自己擁有 `grid`、`towers`、`path`、`sim`。作法：

- 新增 `boardOf(game, p)`：現有模式與接力回傳 `p` 本身；coop 回傳 `game.shared`（`{ grid, path, sim }`）。
- `gameLogic.js` 裡所有碰 `grid / path / sim` 的地方改走 `boardOf`（M1 已完成）。
- **塔的清單不放進棋盤。** `p.towers` 維持「這位玩家擁有的塔」，因為合成、保留、特殊塔配方都只用自己的塔，這些邏輯因此完全不用改。全隊所有塔的聯集（給 `createWave` 與畫面用）留到 M2 決定怎麼取得（例如 `allTowers(game)` 由各玩家的 `p.towers` 串起來），不另外維護第二份清單。
- 塔新增 `owner` 欄位（現有模式 = 玩家自己，行為不變）。
- 這一步**不改任何行為**，先用 `balanceSim.js` 與現有測試做迴歸。

之後想做「2v2」（兩個共用棋盤、各隊一張）只要讓 `boardOf` 依隊伍回傳不同棋盤即可。

### 3.2 後端

| 檔案 | 改動 |
|------|------|
| `config.js` | 新增 `COOP` 區塊（尺寸表、`hpPerPlayer`、`wallHp`、`blockPolicy`、`stoneRemoveBy`）；`coopLayout()` |
| `gameLogic.js` | `boardOf`、`owner`；`startGame` 建共用棋盤；`placeGem` 的衝突判定與依 `blockPolicy` 跳過路線驗證；技能改為全隊共用；結算依 owner 分帳；**建造階段新增每 100ms 的步進**（建造者移動、工作進度），沿用波次的時間步長；復原（`takeSnapshot`）在 coop 改為「取消施工／收回」|
| `builder.js`（新）| 純函式：建造者位置、移動、工作佇列（一次一件）、取消、完成；不碰 socket，可單獨測試 |
| `pathing.js` | 新增 `findFullPathWeighted(board, costOf)`；回傳路徑與突破點。原 BFS 保留 |
| `waveSim.js` | `createWave` 接受 `breach` 設定；`moveMonster` 加入「停下來攻擊牆」；`kill()` 記到 `tower.owner`；`sim.earnedBy`（依擁有者）取代單一 `sim.earned` |
| `index.js` | 新增 `gt:hover`（volatile，轉播給同房）；`gt:frame` 在 coop 對所有人送同一份 |
| `balanceSim.js` | 增加 coop 場景（多個機器人共用一張圖）|

### 3.3 前端

| 檔案 | 改動 |
|------|------|
| `GemBoard.vue` | 以 props 取得尺寸與棋盤；支援擁有者顏色、預定標記、路線預覽、突破點 |
| `useGemCamera.js`（新）| 縮放與平移的**純函式**＋一組輸入轉接。輸入事件先正規化（`{type, x, y, delta}`）再進邏輯，不直接綁滑鼠事件 |
| `GemMiniMap.vue`（新）| 小地圖，點擊跳轉 |
| `GemPlayerTabs.vue` | coop 時隱藏（只有一張圖）|
| `useGemTd.js` | 接建造者事件與 `CELL_TAKEN`；座標轉換集中在一個函式 |
| `GemBuilders.vue`／繪製（新）| 畫各玩家的建造者、施工進度條、灰塵粒子（接 `usePixelFx.js`）；自己的角色在前端預測移動，避免點了沒反應 |
| 手牌區（現有 `GemPanel`）| 畫面下方 5 格寶石，顯示每顆是「待放／施工中／已完成」，施工中點它即取消 |
| 大廳頁 | 新增模式選項 |

## 4. 協定

沿用現有事件，新增最少：

- `gt:place`：簽名不變；新增錯誤碼 `CELL_TAKEN`。
- `gt:move`（client → server）：`{ x, y }`，建造者移動目標。
- `gt:build`（client → server）：`{ slot, x, y }`，指派建造者去某格蓋手牌第 `slot` 顆。
- `gt:cancel-job`（client → server）：無參數，取消目前的施工或拆除，寶石回手牌。
- `gt:demolish`（client → server）：`{ towerId }`，指派拆除。
- 建造者位置與工作進度走 `gt:frame`（volatile，約 10Hz），其餘變動走 `gt:state`。
- `gt:hover`（client → server，volatile）：只在 `instant` 模式使用，`{ x, y }` 或 `null`。
- `gt:state`：coop 時多 `shared` 區塊（棋盤、各塔 owner、預定標記、突破點）。

## 5. 第一版範圍

**做：**
- 2～3 人、一張蛇行大地圖
- 建造者角色：自由移動、每顆寶石施工 3 秒、取消無懲罰、拆除也需要時間（見 2.6）
- 即時共用放置、先到先得
- `breach` 堵死處理＋路線預覽
- 擊殺金依擁有者；技能共用
- 電腦版、滑鼠＋鍵盤

**不做：**
- 手機／觸控
- 4～6 人、多張版型
- 塔交換／贈送
- `solo` 血量、傷害測試、排行榜（先關閉，避免未平衡的成績污染現有榜）
- Steam 連線

## 6. 里程碑

| 階段 | 內容 | 驗收 |
|------|------|------|
| M1 | 共用棋盤抽象（`boardOf`、`owner`），**零行為改變** | 現有模式 `balanceSim` 結果與改前一致 |
| M2 | coop 開局：`coopLayout`、共用 sim、依 owner 分帳；先沿用 `validate` | 兩個機器人能打完一場 |
| M3a | 即時共用放置（`instant`）：衝突、軟鎖、顏色 | 兩個瀏覽器同時放不出現狀態不一致 |
| M3b | 建造者與工作系統（`builder.js`）：移動、施工 3 秒、取消返回手牌、拆除；建造階段 100ms 步進 | 取消後寶石確實回手牌且格子釋放；單元測試涵蓋工作狀態機 |
| M4 | `breach`：加權尋路、拆牆、預覽、突破點 | 全堵死時怪物會拆牆通過；單元測試涵蓋 |
| M5 | 前端相機、小地圖、建造者繪製與動畫（待機浮動、走路擠壓、施工搖晃）、coop 介面 | 40×40 能順暢操作 |
| M6 | 平衡：機器人跑通關率與波數，調 `hpPerPlayer`、`wallHp` | 簡單難度機器人通關率落在合理範圍 |
| M7 | 真人試玩 | 見第 8 節 |

M1 先做，因為它同時降低所有後續階段的風險，也最容易獨立合併。

## 7. 保留的彈性

| 未來需求 | 現在先留什麼 |
|----------|-------------|
| 手機版 | 相機邏輯是純函式、輸入先正規化；座標轉換集中一處；手機進入 coop 時顯示「請用電腦」而非壞掉 |
| 多隊／2v2 | `boardOf` 可依隊伍回傳不同棋盤；`playerIds` 不假設只有一張圖 |
| 4～6 人 | `COOP` 尺寸表與 `coopLayout(n)` 已參數化 |
| 多張版型 | `coopLayout` 簽名固定，版型是資料 |
| 塔交換／贈送 | `tower.owner` 已存在 |
| 塔受傷 | 塔的 `hp` 欄位可為 `null`，`breach` 對塔的處理集中在一個函式 |
| 堵死策略切換 | `blockPolicy` 是設定，兩種都保留 |
| Steam 單機／Listen server | 模擬仍是純函式、不碰 socket |
| 回放與驗證 | 放置與拆牆是明確的事件，可記錄成序列 |

## 8. 試玩要看什麼

- 完成率與平均波數（和各自地圖的現有模式比）
- 「路被堵死」發生的頻率、拆牆是否變成固定套路
- 放置衝突（`CELL_TAKEN`）次數與玩家反應
- 惡意堵路或搗亂的實際發生情況
- 問卷：有沒有想和朋友再玩？覺得比各自地圖更有合作感嗎？

達標條件由你定義；建議至少 5 場 2～3 人局、其中有兩場以上不是你自己的朋友圈。

## 9. 待決定

1. 突破點是塔時的處理（見 2.5）。
2. 技能共用還是各人獨立；本文暫定共用。
3. 傷害測試與排行榜在 coop 是否另開一個榜（暫定先關閉）。
4. 怪物血量人數加成的初始值（暫定 +80%/人，等 M6 定案）。
5. 路徑點數量與地圖長度是否需要同步調整怪物速度。
6. 施工完成但尚未選保留的寶石能否收回（見 2.6，建議可以、免費瞬間）。
7. 建造秒數預設值與 `builderSpeed`、`buildSeconds` 的實測值。
8. 波次中是否允許建造者補牆（第二版；第一版不行）。
9. 研究是否新增「移動速度」項目作為金幣出口（第二版）。
