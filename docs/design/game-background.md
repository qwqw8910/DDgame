# 山中別館殺人事件(暫名)— 遊戲背景與設計分析

> 類型:網頁版社交推理 / 說謊遊戲
> 目標玩家:朋友線上聚會(3–6 人,私人房間,邀請連結加入)
> 討論方式:網頁只提供計時器與流程,語音由玩家自行處理(Discord / LINE 等)
> MVP 範圍:Level 1–2(殺人魔 + 客人 + 共犯)

---

## 一、故事背景

故事發生在一座偏僻的山中別館。

賓客受主人邀請來到別館,當晚主人被殺。警察無法立刻趕到,而最恐怖的是:**殺人魔就在賓客之中**。

在警察到達之前,大家決定先把最可疑的人關進地下的鍋爐室。問題是,沒有人知道誰才是殺人魔。

玩家只能依靠:

**目擊情報 + 玩家說詞 + 角色能力 + 推理**

找出殺人魔躲在哪個地點。

---

## 二、核心設計重點(給設計者)

| 特色 | 說明 | 對網頁版的意義 |
| --- | --- | --- |
| 投票對象是「地點」而非玩家 | 每位玩家對應一個地點,大家投「畫廊」而非「小明」 | UI 以地點為單位呈現,玩家頭像附著在地點上 |
| 情報來自「傳牌」 | 看 2 張留 1 張,另一張傳給任一尚無角色的人,並宣稱「我看到 X 來到你的房間」 | 傳牌順序與去向是核心資訊,需完整記錄供結算後復盤 |
| 說謊是規則的一部分 | 可說謊的對象包含自己的角色、傳牌內容、目擊情報 | 系統不判斷真偽,只保證「牌的真實狀態」不外洩 |
| 討論時間刻意很短(約 3 分鐘) | 時間越長,資訊越容易被完全推導 | 計時器是核心元件,時間可由房主調整 |
| 客房可能藏著角色 | 最後一位玩家兩張牌一張自留、一張放客房,殺人魔可能在客房 | 客房與鍋爐室固定在畫面中央 |
| 陣營不對稱 | 好人 / 殺人魔陣營 / 第三方(炸彈客) | 結算畫面需清楚說明誰贏、為什麼 |

## 三、遊戲元件

| 元件 | 數量 | 用途 |
| --- | --- | --- |
| 角色牌 | 11 | 殺人魔、共犯、炸彈客、律師、富商、偵探、管家、客人 ×4 |
| 角色板塊 | 11 | 公開本局出現的角色種類(只告知有哪些,不告知在誰手上) |
| 地點牌 | 8 | 交誼廳、畫廊、撞球室、書房、玄關、餐廳、客房、鍋爐室 |
| 投票牌 | 36 | 6 種顏色 × 6 張,顏色對應地點 |

- 客房、鍋爐室固定放在中央,其餘 6 個地點分給玩家。
- 客人顏色:黃、藍、紅、綠、紫各 1(最多 5 色不重複);6 人局的第 6 位客人會重複用黃,僅用於討論時辨識(例如「我看到藍色客人被傳走」)。

## 四、角色一覽

| 角色 | 陣營 | 能力 / 特性 | 勝利條件 | 階段 |
| --- | --- | --- | --- | --- |
| 客人 | 好人 | 無特殊能力 | 殺人魔進鍋爐室 | MVP |
| 殺人魔 | 殺人魔陣營 | 可說謊、誤導 | 殺人魔**不**進鍋爐室 | MVP |
| 共犯 | 殺人魔陣營 | 不一定知道誰是殺人魔;可假扮殺人魔或製造假嫌疑人 | 同殺人魔 | MVP(Level 2) |
| 炸彈客 | 第三方 | 裝成殺人魔 | 自己被送進鍋爐室(單獨獲勝,其他人勝利條件全部失效) | 後續 |
| 律師 | 好人 | 開票後公開身份;他投給誰,該玩家原本投出的 1 票無效 | 殺人魔進鍋爐室 | 後續 |
| 富商 | 好人 | 開票時可公開身份,自己的票算 2 票 | 殺人魔進鍋爐室 | 後續 |
| 偵探 | 好人 | 討論階段公開身份,指定一人,其角色直接進鍋爐室並判定勝負 | 殺人魔進鍋爐室 | 後續 |
| 管家 | 好人 | 高難度模式:開局另放 2 張「事前離開」的角色牌在鍋爐室旁;公開後可查看,但失去投票權 | 殺人魔進鍋爐室 | 後續 |

說明:

- 律師無效的是「那一票」,不是「那個人被投掉」。
- 偵探判錯會直接讓殺人魔逃脫,是高風險高報酬角色。
- 管家需在「保留投票權」與「取得離場情報」之間二選一。

## 五、遊戲流程

### 1. 準備

1. 選擇難度(Level 1–8;新手建議 Level 1)。
2. 中央放客房與鍋爐室,其餘地點洗牌後每人一張。
3. 每位玩家拿取與自己地點同色的投票牌。
4. 角色牌數量 = 玩家數 + 1(Level 1、4 人時為殺人魔 ×1 + 客人 ×4,共 5 張)。多出的 1 張最後進客房。
5. 翻開對應的角色板塊,公開本局有哪些角色。

### 2. 目擊與選擇(傳牌階段)

1. 第一位玩家從牌堆抽 2 張,偷看後留 1 張蓋在自己的地點,另 1 張傳給任一尚未持有角色的玩家,並口頭說出「目擊情報」(例如「我看到殺人魔來到書房」,**可以說謊**)。
2. 收到牌的玩家再從牌堆抽 1 張,與收到的牌二選一留下,剩下的再傳給另一位尚無角色的玩家。**收到牌的玩家必須知道哪一張是上一位玩家傳來的**(網頁上牌面標示「來自 玩家X」與「剛抽到」)。其中「來自上一位玩家」的牌**直接開著**顯示(因為上一位玩家傳牌時一定會口頭講出傳了什麼,開牌可以直接比對有沒有說謊);自己剛抽到的牌維持**蓋著**,要點一下才會翻面。
3. 傳遞對象**不必是隔壁**,可任意指定(例如 A → C → B → D),使資訊更混亂。
4. 最後一位玩家:收到的牌 + 牌堆抽的牌二選一自留,另一張放進客房。
5. 輪到自己選牌時,「確認傳牌」固定要等 10~15 秒才能按下(目前設定 12 秒),讓殺人魔 / 共犯等壞人也有時間想好說法。

### 3. 討論階段

- 建議上限約 3 分鐘。
- 可說任何事,包含角色、傳牌內容、目擊情報、指控他人,甚至「我剛才說謊」。
- 能力類角色(偵探、管家等)在此階段公開。
- 推理核心:不是找「誰說得最像」,而是把所有人的傳牌路徑串在一起,找出矛盾。

### 4. 投票與結算

1. 玩家以投票牌對「地點」投票(投的是殺人魔可能所在的位置),客房也可以投。
2. 開票;律師、富商此時公開並影響票數。
3. 得票最高的地點,其角色牌被送進鍋爐室。
4. 依鍋爐室內的角色判定勝負。

## 六、Idea Refine 分析

### Problem Statement

我們該如何讓一群朋友在網頁上,不靠實體牌也能體驗「傳牌、說謊、互相拆穿」的社交推理樂趣,且系統既保證隱藏資訊安全,又不干擾玩家之間自由的說謊與討論?

### Phase 1:設計變體(發散)

| 視角 | 變體 | 判斷 |
| --- | --- | --- |
| 簡化 | 純計時器 + 隱藏資訊分發器,所有對話走外部語音 | **採用**:成本最低,保留遊戲精髓 |
| 反向 | 傳牌時「目擊情報」改為在系統內結構化輸入(選角色 + 選地點) | 列為選配:可留下復盤紀錄,但會削弱口頭說謊的臨場感 |
| 受眾轉換 | 單人對 AI 模式 | 暫不做:AI 說謊與推理難度高 |
| 組合 | 結算後附「真相回放」(誰傳了什麼給誰、誰在說謊) | **建議納入**:最能製造「原來你騙我!」的社交樂趣 |
| 10 倍規模 | 公開大廳配對、排名、戰績 | 暫不做:需防作弊、處理離線 |
| 專家視角 | 桌遊玩家認為最有趣的是「傳牌順序造成的資訊不對稱」 | 傳牌 UI 是產品核心,應優先打磨 |

### Phase 2:收斂方向與壓力測試

**方向 A(推薦):私人房間「流程主持人」**
網頁只扮演發牌員與主持人:分發隱藏資訊、驅動傳牌流程、計時、收集投票、結算、真相回放。

- 使用者價值:解決朋友遠距玩實體桌遊的痛點(不需要有人持有桌遊、不需要主持)。
- 可行性:高。主要難點是伺服器端維護隱藏狀態與即時同步。
- 差異化:免安裝、邀請連結即玩;弱點是核心體驗仰賴外部語音。

**方向 B:內建聊天 + 結構化目擊情報**
體驗更完整、可完整復盤,但需處理聊天、說謊紀錄與操作負擔,MVP 成本明顯較高。

**方向 C:公開配對大廳**
擴大玩家池,但陌生人局的氣氛與惡意玩家問題會掩蓋核心玩法驗證,不適合 MVP。

結論:先做方向 A,把「傳牌、投票、結算」跑順,再評估是否加入方向 B 的元素。

### Recommended Direction

做一個以私人房間為單位的網頁遊戲,3–6 位朋友透過連結加入,自行開語音。系統負責發牌、傳牌流程、3 分鐘計時、投票、結算與真相回放。MVP 只含客人、殺人魔、共犯三種角色,先驗證「傳牌 + 目擊情報」循環是否好玩。

### Key Assumptions to Validate

- [ ] 玩家願意在外部語音中自行討論,不需要內建聊天——找 2–3 組朋友實測,觀察是否抱怨「不方便說話」。
- [ ] 傳牌流程在網頁上直覺,不會因為看不到彼此的動作而失去「資訊混亂」的樂趣——做低擬真原型,測玩家是否能理解「誰傳給誰」。
- [ ] Level 1–2 的配置已足夠有趣——玩 5 局以上,看玩家是否想要更多角色。
- [ ] 真相回放能顯著提高重玩意願——比較有無回放時的「再來一局」比例。
- [ ] 隱藏資訊不會在前端洩漏——審查網路封包與狀態同步,確認他人角色牌永不傳到客戶端。

### MVP Scope

**包含**

- 建立房間 / 邀請連結 / 3–6 人加入
- 地點隨機分配(客房、鍋爐室固定)
- 角色:殺人魔、客人(含顏色)、共犯
- 傳牌流程:抽牌、二選一、指定傳給任一尚無角色者、客房收尾
- 3 分鐘討論計時器(房主可調整)
- 對地點投票、開票、鍋爐室結算與勝負判定
- 結算後真相回放

**不含**:炸彈客、律師、富商、偵探、管家(列入後續版本)。

### Not Doing(以及原因)

- 內建聊天 / 語音:語音由玩家自理,開發成本高、價值未驗證。
- 公開配對與排名:會被陌生人與惡意行為干擾,先驗證朋友局體驗。
- AI 玩家:說謊與推理品質難以保證,且與社交樂趣定位不同。
- 帳號系統:用暱稱 + 房間連結即可,降低進入門檻。
- Level 3–8 與特殊角色:待核心循環驗證後逐一加入。
- 系統判定「說謊」:說謊是遊戲本質,系統只保證牌的真實狀態。

### Open Questions

1. 玩家人數範圍:地點 8 張(中央固定 2 張)與投票牌 6 色推算最多 6 人,最少幾人?是否需要為少人局調整規則?
2. 殺人魔 / 共犯是否在開局知道彼此?(原文只說共犯「不一定知道誰是真正殺人魔」,需確認)
3. 投票規則細節:每人幾張票?能否投自己的地點?客房是否可以被投?
4. 平票如何處理?
5. Level 2 的角色配置在原規則中如何定義?(目前暫定為殺人魔 + 共犯 + 客人)
6. 目擊情報在 MVP 是否要有輕量的結構化紀錄(僅供結算回放使用),或完全不記錄?
7. 斷線與重連:傳牌階段玩家掉線時,是否由房主代為處理、暫停或替補?
8. 美術與題材:暫定「山中別館」的推理氛圍,是否沿用原作風格需另行確認版權與命名。

## 七、實作對照(2026-10)

- 前端 `vue-app/src/apps/mountain-lodge/`,後端 `server/mountain-lodge/`(namespace `/mountain-lodge`),房間走統一房間模組。
- DB:沿用 `rooms`(`app_id='mountain-lodge'`、`max_players` 3–6)與 `players`(`score` = 累計勝場),**未新增資料表**;牌桌狀態只存記憶體,server 重啟後房間回到大廳。
- 房間設定(房主在大廳調整):難度 Level 1/2、討論時間 1–5 分鐘(預設 3 分鐘)。
- Open Questions 的暫定值(集中於 `gameLogic.js` 頂部,可改):
  1. 人數 3–6 人,少人局不調整規則。
  2. 殺人魔與共犯互不相識。
  3. 每人 1 票,可投自己的地點,也可以投客房;鍋爐室不可投;票數於全員投完或房主強制開票時結算。
  4. 平票:同票最高的地點,其角色牌全部進鍋爐室(其中有殺人魔 → 好人勝);無人投票 → 殺人魔陣營勝。
  5. Level 2 = 殺人魔 + 共犯 + 客人。
  6. 目擊情報不記錄,真相回放只列實際的抽牌 / 留牌 / 傳牌。
  7. 斷線:牌局保留、重連補發;輪到離線者時房主可「代為隨機傳牌」;玩家主動離開或被踢 → 本局中止回大廳。
  8. 客人顏色 5 人局前(黃、藍、紅、綠、紫)皆不重複;僅 6 人局的第 6 位客人會重複用黃。
  9. 傳牌鎖定時間:前端常數 `MIN_PASS_SECONDS = 12`(`vue-app/src/apps/mountain-lodge/data/constants.js`),純前端 UI 限制,未在 server 端強制。
