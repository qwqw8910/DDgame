> 狀態：規劃已確認（2026-10-16）；**Phase 1、Phase 2 已實作（2026-10-16）**，尚未在真實瀏覽器做視覺 / 多人實測，`DEV_BOTS` 仍為 `true`。決定事項見第 11 節；仍標記 ⚠️ 的項目屬於後期範圍。

## 1. 先回答核心問題：網頁版有沒有說書人？

**有，而且主流做法都是「真人說書人 + 系統輔助」。** 網路上的實作大致分三類：

| 類型 | 代表 | 說書人是誰 | 系統做什麼 | 優缺點 |
|---|---|---|---|---|
| **真人說書人工具（魔典型）** | 集石線上魔典、Town Square、botc.app | 一位真人，不參與遊戲 | 魔典（Grimoire）、夜晚順序表、提醒標記、發角色、投票計數、同步公開狀態 | 保留遊戲精髓（說書人調整局勢、給假資訊）；需要一個人專門主持 |
| **AI / 自動說書人** | 天天血染鐘樓、手狼「AI 說書人版」 | 系統 | 自動分配、自動結算夜晚能力、自動決定醉酒／中毒給的假資訊 | 不需主持人；但假資訊多半是隨機或固定規則，失去「說書人讓遊戲精彩」的部分，實作量極大 |
| **混合型** | （本專案建議） | 真人，系統大量代勞 | 魔典之外，系統還會：算出「真實答案」建議、提醒誰中毒／醉酒、檢查配置合法性、自動執行硬規則 | 說書人只需做「判斷」，不必做「記帳」 |

Town Square 的同步設計值得直接參考：**說書人端是唯一真實來源**，一般角色不會出現在廣播狀態裡，只透過「點對點私訊」發給該玩家本人；提醒標記（reminder）永遠不同步給玩家。這和山中別館 `buildView(game, playerId)`「伺服器只推玩家有權看到的內容」是同一個思路，可以直接沿用。

### 本專案建議

- **每一場都必須有一位真人說書人（混合型）**。說書人由房主在大廳指定或隨機抽出（見 3.2），不入座、不算玩家。
- **之後（Phase 4）：可選「自動說書人」**，只針對《暗流湧動》，假資訊用規則產生（見第 9 節）。

## 2. 說書人的權力如何平衡

血染鐘樓的說書人本來就有很大的裁量權（選假資訊、決定醉酒者看到什麼、設定開局），這是遊戲設計的一部分，**不需要也不應該拿掉**。網頁版要做的是：**把「規則規定的事」交給系統強制執行，把「規則允許說書人決定的事」留給說書人，並讓所有決定事後可被檢視。**

### 2.1 四層權限劃分

| 層級 | 誰決定 | 內容 | 系統行為 |
|---|---|---|---|
| **硬規則**（系統強制） | 系統 | 投票計數與處決門檻、死亡玩家只有一張幽靈票、每人每天只能提名一次／被提名一次、存活人數、勝負判定（惡魔死亡 / 剩 2 人） | 說書人無法改動；違規操作直接被伺服器拒絕 |
| **玩家選擇**（系統自動記錄） | 玩家 | 投毒者毒誰、僧侶保護誰、小惡魔殺誰、管家選誰當主人 | 玩家在畫面上點選，系統自動放對應提醒標記（見 7.3）；說書人可撤銷，撤銷會記錄在日誌 |
| **規則內裁量**（說書人決定，系統輔助） | 說書人 | 醉酒／中毒時給什麼資訊、間諜／隱士被當成什麼、開局配置（男爵 +2 外來者等）、惡魔的 3 張偽裝（Bluffs）、紅唇女郎接手、守鴉人看到的角色 | 系統先算好「真實答案」當預設值，說書人可改；改成和真實答案不同時，UI 標示「⚠ 給假資訊」並記錄在日誌 |
| **主持流程**（說書人決定） | 說書人 | 白天討論多久、何時開放提名、何時入夜、催促發言 | 系統提供計時器與按鈕，不強制 |

### 2.2 平衡機制

1. **說書人不是玩家**：說書人不入座、不投票、不算勝負、不計分（`players.score` 只給玩家）。沒有立場，就沒有偏袒動機。
2. **系統提供真實答案**（Phase 2）：洗衣婦、廚師、共情者、占卜師等資訊角色，系統依魔典即時算出正確答案。說書人「照實給」只要按一下；要給假的才需要手動改。降低說書人疏忽犯錯的機率。
3. **合法性檢查**：開局配置會檢查人數對應的角色數量（見第 6 節）、男爵／酒鬼等「影響開局」角色是否正確調整，不合法時阻擋開始（可強制略過，但會記錄）。
4. **所有決定都進日誌，終局公開**：每一筆夜晚行動、給出的資訊（含真／假標記）、提醒標記變動，都寫進 `log`。終局時所有人可以看「完整魔典 + 時間軸回放」——說書人知道事後會被看到，自然會公正。（參考山中別館已有的 `LodgeReplay.vue`）
5. **防止時間差洩漏資訊**：夜晚時「所有玩家畫面都一樣是入睡畫面」，被喚醒者的提示以彈窗疊加，不改變外觀節奏；說書人送出的 prompt / 資訊會在伺服器端隨機延遲 0–1.5 秒才推給玩家（Phase 2）。避免玩家從「誰的畫面在動」推理出角色。
6. **說書人平衡提示（非強制）**：說書人面板顯示「目前善惡存活比」「惡魔是否已被高度懷疑」等指標，提醒說書人讓遊戲保持接近（官方 Storyteller Advice 的核心精神：讓兩邊都有機會贏）。
7. **說書人交接保護**：魔典權限綁在遊戲狀態的 `storytellerId`，**不綁房主**。房主轉移不會讓任何人拿到魔典。遊戲中說書人只能把身份交給觀戰者（不能交給已入座玩家）；說書人斷線時遊戲暫停，等說書人回來（見 3.3）。

## 3. 房間機制（沿用 `server/room`，對照山中別館）

### 3.1 基本設定

| 項目 | 值 |
|---|---|
| App slug | `clocktower`（前端 `vue-app/src/apps/clocktower/`，後端 `server/clocktower/`） |
| Socket namespace | `/clocktower` |
| 遊戲事件前綴 | `ct:*`（例：`ct:state`、`ct:start`、`ct:nominate`） |
| 路由 | `/clocktower`（大廳）、`/clocktower/room`（房間） |
| Supabase | 沿用 `rooms` / `players` 表；`rooms.app_id = 'clocktower'` |
| 人數 | 座位 **5～15 人** + 1 位說書人；`max_players` = 座位上限 + 1。建房時選的是「座位上限」，實際開局人數 = 開始時已入座的人數（至少 5 人），第 6 節的配置表依實際人數套用 |
| 分享連結 | `#/clocktower?room=XXXXXX`（同山中別館） |

⚠️ 旅行者（Traveler）可讓人數到 20 人並允許中途加入，MVP 不做。

### 3.2 流程

- **LobbyPage**：完全複製 `MountainLodgeLobbyPage.vue` 的結構——建立房間（暱稱 + 座位人數 5–15）、加入房間（6 碼房間碼 + 暱稱）；Lobby 只做輸入驗證 + 路由跳轉。
- **建立者 = 房主**。房主負責房間管理（踢人、設定、指定說書人），房主本身也可以當玩家。
- **決定說書人**（大廳階段，房主操作，二選一）：
  - **指定**：在玩家清單上點某人 →「設為說書人」（可以指定自己）。
  - **隨機**：按「隨機抽說書人」，從房內所有人抽一位。
  - 開始遊戲前一定要有說書人，否則「開始」按鈕不能按。
  - 說書人決定後，畫面切換為說書人視角，由說書人接手設定劇本與角色（第 6 節）。
- **RoomPage 大廳階段**：玩家進房後自行點選空座位入座（Town Square 的 `claim` 做法），說書人不入座。說書人可拖曳調整座位；座位順序就是遊戲裡的「鄰座」，所以一定要在開始前確定。
- **遊戲中的權限**：所有遊戲流程操作（入夜、喚醒、標記死亡、宣告勝利、回大廳）都檢查 `storytellerId`，不檢查房主。房主若是玩家，遊戲中和其他玩家權限相同。
- **觀戰**：沿用 `canJoinAsPlayer` / `spectatorCanUpgrade` hook——遊戲進行中新加入者成為觀戰者，只看到公開城鎮廣場。
- **重連**：同 playerId 重連時補發該玩家的私人視圖（角色、夜晚資訊、有權看的聊天紀錄）。
- **大廳文案**：寫明「公開討論請進 Discord 語音，私聊與所有操作在網頁上」「請使用和 Discord 相同的暱稱」「夜晚請關麥克風」「不可出示角色牌或截圖」。
- **開始條件**（說書人按「開始」時伺服器檢查）：已指定說書人、已入座 ≥ 5 人、配置合法（第 6 節）。房內**沒入座也不是說書人的人，開始時自動轉為觀戰者**。
- **斷線**：一般玩家斷線，遊戲繼續，座位保留，重連後補發。輪到斷線玩家行動（被喚醒、投票）時，說書人可以等待，或在說書人面板「代為選擇」（寫進日誌）。
- **遊戲中玩家主動離開 / 被踢**：不中止遊戲（一局很長，中止代價太大）。座位保留並標示「🚪 已離開」，視同死亡且沒有幽靈票；說書人可在魔典上處理（例如該座位是惡魔時，宣告勝負）。離開的人重新進房只能觀戰（現有 `canJoinAsPlayer` 行為）。
- **觀戰者**：可以看公開城鎮廣場、公開文字、私聊連線；**不能發言、不能私聊、不能私訊說書人**。

### 3.3 共用房間模組：不需要修改

`server/room/index.js` 會在房主斷線 30 秒後自動 `transferHostToNext()`，也允許房主隨時 `room:transfer-host`。如果「房主 = 說書人」，這會讓玩家拿到魔典；但本設計把說書人身份放在遊戲狀態的 `storytellerId`，和 `room.host_player_id` 無關，所以：

- 房主轉移只影響房間管理權，**魔典不會跟著轉移**。
- 說書人斷線：在本遊戲的 `onPlayerLeft(roomId, playerId, 'disconnect')` hook 裡判斷，若是說書人 → 遊戲進入 `paused`，所有人看到「等待說書人重新連線」。說書人用同一個 playerId 重連 → 恢復原階段。
- 說書人主動離開 / 被踢：遊戲中止回大廳，所有人看到「說書人離開，本局中止」（沒有說書人就無法繼續）。
- 遊戲中交接說書人：用遊戲事件 `ct:transfer-storyteller`，目標只能是觀戰者。

結論：**只使用現有 hooks（`canJoinAsPlayer`、`spectatorCanUpgrade`、`buildGameState`、`onPlayerJoined`、`onPlayerLeft`、`onSpectatorUpgraded`），不動 `server/room/`**，其他遊戲（懂我再說、字元風暴、山中別館）不受影響。

若之後仍需要改共用模組，規則是：只新增可選 hook，未設定時維持原行為，並在改完後跑 `server/room/*.test.js`、`server/mountain-lodge/*.test.js` 與其他遊戲的既有測試，全部通過才算完成。

說書人雖然在 `players` 表裡，但**不放進座位 `seats`**，也不參與 `players.score` 計分。

## 4. 圖片替換設計（★ 單一公用登記處）

### 4.1 原則

- 現在全部用 **emoji / 簡單 icon**，之後換成真圖片。
- **所有視覺素材只在 `apps/clocktower/data/assets.js` 登記一次**，其他元件一律透過 `RoleToken.vue` / `GameIcon.vue` 顯示，**元件內不准直接寫 emoji 或圖片路徑**。
- 規則資料（能力文字、夜晚順序）和視覺資料（圖示）分開：規則在 server 的 `roles.json`，圖示在前端 `assets.js`，兩邊用角色 `id` 對應。換圖完全不碰遊戲邏輯。

```js
// 唯一的路徑解析函式：img === true → 依慣例組路徑；字串 → 直接用；其他 → null
export function resolveImg(category, id, entry) {
  if (!entry?.img) return null
  return entry.img === true ? `${BASE}${category}/${id}.webp` : entry.img
}
```

### 4.3 圖檔命名慣例

```
vue-app/public/clocktower/
├── roles/<roleId>.webp        例：roles/imp.webp
├── reminders/<roleId>-<name>.webp
├── teams/<team>.webp
└── ui/<name>.webp             例：ui/night.webp、ui/banner.webp
```

- 建議 webp、角色圖透明背景、正方形（Town Square 也要求透明背景 PNG）。
- `RoleToken.vue` 規格：`props: { roleId, size }`；有圖顯示 `<img>`，沒圖顯示 emoji；圖片載入失敗（`@error`）也退回 emoji。外框顏色依陣營。
- ⚠️ 之後若有自訂劇本 / 自製角色，`roles.json` 的角色可帶 `image` URL（相容官方格式），`RoleToken` 優先順序：`assets.js` 的 img → 劇本 `image` → emoji → 陣營預設 icon。

## 7. 遊戲流程

### 7.1 夜晚

- 全體玩家畫面切換成同一個「入夜」畫面（遮住城鎮廣場，只能看自己角色與規則表）。
- 說書人面板顯示 `NightQueue`：依 `firstNight` / `otherNight` 排序、**只列出在場且存活（或能力仍有效）的角色**，每一列有：
  - 角色、座位、夜晚提示文字（`firstNightReminder`）
  - 是否中毒 / 醉酒的警示
  - 「喚醒」按鈕 → 對該玩家送出 prompt
  - 「完成」打勾
- 首夜固定項目：爪牙互認、惡魔得知爪牙與 3 張偽裝（7 人以上，系統自動送出，說書人確認即可）。
- 說書人按「天亮」→ 系統公布昨晚死亡名單（由說書人在魔典標記的死亡，系統不自動殺人）。

### 7.2 喚醒互動類型（`prompt.type`）

| 類型 | 例子 | 玩家端 | 說書人端 |
|---|---|---|---|
| `choose-player` (n 人) | 投毒者、僧侶、小惡魔、占卜師、管家 | 在圓桌上點選 n 位 → 送出 | 看到選擇；系統**依玩家選擇自動放提醒標記**（見 7.3），說書人只需確認 |
| `info-number` | 廚師、共情者 | 彈窗顯示數字 | 預填真實答案，可改 |
| `info-players-role` | 洗衣婦、圖書管理員、調查員 | 顯示「這兩位之一是 ○○」 | 預填（真角色 + 隨機另一人），可改 |
| `info-yes-no` | 占卜師結果 | 顯示「是 / 否」 | 預填真實答案（含紅鯡魚） |
| `info-role` | 送葬者、守鴉人 | 顯示角色 | 預填 |
| `info-grimoire` | 間諜 | 唯讀魔典快照 | 一鍵送出 |
| `custom` | 任何特殊情況 | 顯示說書人輸入的文字 / 圖示 | 自由輸入 |

> 系統計算「真實答案」時，若該玩家帶有中毒 / 醉酒標記，預填欄位旁顯示「⚠ 此玩家目前失去能力，可給任意資訊」。
>
> **Phase 1**：`info-*` 的介面都要做（說書人選數字 / 玩家 / 角色 / 是否後送出），但**欄位是空的**，由說書人看魔典自己填；「真實答案預填」與「⚠ 給假資訊」標示是 Phase 2。中毒 / 醉酒警示在 Phase 1 就要顯示（直接讀提醒標記即可）。

### 7.3 自動提醒標記

「誰中毒、誰受保護、誰被攻擊」是**玩家的選擇**，不是說書人的決定。所以這類標記由系統依玩家的 `ct:prompt-reply` 自動放置，說書人不需要手動操作。

| 角色 | 玩家選擇 | 系統自動放的標記 | 自動移除時機 |
|---|---|---|---|
| 投毒者 | 選 1 位 | 目標身上「☠️ 中毒」 | 下一個夜晚投毒者再次行動前 |
| 僧侶 | 選 1 位（不能選自己） | 目標身上「✋ 受保護」 | 天亮後 |
| 小惡魔 | 選 1 位 | 目標身上「🗡️ 攻擊目標」（**不會自動死亡**） | 天亮結算後 |
| 管家 | 選 1 位主人 | 目標身上「🤵 主人」 | 下一個夜晚管家再次行動前 |
| 占卜師 | 選 2 位 | 不放標記，直接進入資訊預填 | — |

規則：

- **說書人可以撤銷或修改任何自動標記**（例如投毒者本身中毒、能力失效時，說書人移除「中毒」標記）。撤銷會寫進日誌，終局公開。
- 若行動者本身帶有中毒 / 醉酒標記，系統**仍會放標記，但改成灰色「⚠ 能力可能無效」**，交給說書人決定要不要生效。
- **死亡一律由說書人確認**：小惡魔的攻擊只放「攻擊目標」標記。天亮前，說書人面板列出「預計死亡：XXX（受保護 / 士兵 / 鎮長等狀況已標示）」，說書人按確認才真正死亡。原因是士兵、鎮長轉移、紅唇女郎、小惡魔自殺傳位都需要人判斷。
- 開局才會出現的標記（酒鬼、占卜師的紅鯡魚）由說書人在 setup 階段指定，系統不自動產生。
- 這些自動化規則寫在 `roles.json` 的自訂欄位 `autoReminder`，例如投毒者：`{ "on": "choose", "reminder": "poisoner:poisoned", "clear": "nextOwnAction" }`。新增角色時照格式補上即可，不必改程式。

### 7.4 白天

**溝通分工：公開討論用 Discord 語音；私聊與所有遊戲操作都在網頁上**（聊天系統細節見 7.6）。這與社群最常見的「Town Square 網頁 + Discord」做法一致，差別是私聊從「切換 Discord 頻道」改成「網頁私聊群組」，所以網頁能在圓桌上畫出誰在跟誰聊，終局也能回放。

白天分成三個小階段，由說書人按按鈕推進，有倒數計時，說書人可以延長（+1 分鐘）或提前結束。**倒數到 0 不會自動切換**，只會提醒說書人（畫面閃爍 + 音效），由說書人決定何時推進（符合 2.1「主持流程由說書人決定」）：

| 小階段 `daySubPhase` | 預設時間 | Discord 語音 | 網頁公開文字 | 私聊群組 | 私訊說書人 | 圓桌顯示 |
|---|---|---|---|---|---|---|
| `dawn` 天亮 | — | 說書人宣布 | 系統公告昨晚死亡名單 | 關閉 | 開放 | 死亡標記 |
| `free` 自由時間 | 8 分鐘 | **公開討論** | 開放（輔助） | **開放** | 開放 | **私聊中的玩家之間畫出連線**，所有人都看得到 |
| `nomination` 提名與投票 | 不限 | 提名發言、辯護 | 開放（輔助） | 關閉（訊息仍可閱讀） | 開放 | 提名箭頭、投票指針 |

- 「自由時間」相當於實體遊戲中大家在城鎮裡走動、有人拉到旁邊私聊的時段。說書人按「集合提名」= Discord 社群裡把所有人拉回城鎮廣場頻道。
- 在網頁私聊的玩家仍聽得到 Discord 公開討論，等於實體遊戲「一邊私聊一邊聽大家講」，可以接受。
- 夜晚：網頁公開文字與私聊群組關閉，只剩私訊說書人。網頁會顯示「🌙 入夜，請在 Discord 關閉麥克風」提示（網頁管不到 Discord，靠自律）。
- 死亡玩家照規則仍可以公開發言、參加私聊。

**提名與投票：**

- 說書人按「開放提名」。
- **提名**：存活玩家點選目標提名（每人每天限提名 1 次、每人每天限被提名 1 次，系統強制）。
- **提名發言**：提名成立後，網頁標示「提名者發言中 → 被提名者辯護中」，兩人在 Discord 語音發言，說書人按「開始投票」才進入投票。
- **投票**（參考 Town Square 的時鐘指針）：
  - 說書人按「開始投票」後，指針從被提名者的下一位開始，**自動**順時針每 1 秒移動一位（說書人可調速度、暫停）；最後一位是被提名者本人。
  - 指針到達前，玩家可以隨時舉手 / 放下；指針經過後該座位鎖定，不能再改。
  - 死亡玩家：還有幽靈票才能舉手；指針經過時若舉手，幽靈票自動用掉。
  - 已離開（`hasLeft`）的座位直接跳過。
  - 說書人可以代任何座位舉手 / 放下（處理斷線玩家，寫進日誌）。
  - 管家：Phase 1 只在管家畫面提示「你只能在主人舉手時舉手」，系統不強制（實際上管家可能中毒，交給說書人判斷）。
- **處決門檻**：票數 ≥ ⌈存活人數 ÷ 2⌉，且**嚴格高於**當日其他提名的最高票。和目前最高票同票 → 雙方都不處決（`onTheBlock = null`）。系統即時顯示「目前將被處決：XXX」或「目前沒有人會被處決」。
- 說書人按「結束白天」→ 系統處決 `onTheBlock` 的玩家並檢查勝負 → 入夜。說書人可以在按之前攔截（例如聖徒被處決、貞潔者、鎮長等需人工判斷的效果），改用「宣告勝利」或手動標記。
- 說書人也可以不經投票直接「標記死亡」（例如獵手開槍、貞潔者觸發），這些都寫進日誌。

### 7.5 勝負判定

- 系統在**每次有人死亡後**（天亮公布、處決、說書人手動標記）自動檢查硬條件：惡魔死亡（且無紅唇女郎接手）→ 善良勝；存活剩 2 人且惡魔活著 → 邪惡勝。
- 自動判定不直接結束遊戲，而是跳出「系統判定：善良陣營獲勝，確認？」給說書人，說書人可以按「確認」或「先不要」（例如說書人要先處理紅唇女郎接手：用 `ct:change-role` 把紅唇女郎改成小惡魔後，再重新判定）。
- 特殊勝負（聖徒被處決、鎮長勝利等）由說書人按「宣告勝利」選擇陣營，並寫進日誌。
- 終局 → `result` 階段：全部角色公開、魔典與日誌回放、勝方 `players.score +1`（同山中別館 `awardScores`）。

### 7.6 聊天系統（網頁私聊 + Discord 公開語音）

#### 技術選擇

- **經伺服器轉送，不做 P2P**：沿用現有 Socket.io，連線本身是 wss 加密。不做 WebRTC P2P，原因：
  1. P2P 要處理 NAT 穿透、斷線重連，複雜很多；
  2. 伺服器必須知道「誰跟誰在私聊」才能在圓桌畫線；
  3. 斷線重連要補發歷史訊息，P2P 做不到。
- **不進 DB**：全部存在伺服器記憶體 `game.chat`，斷線重連補發；回到大廳或房間封存時清除。
- **公開語音交給 Discord**：網頁不做語音。網頁內建語音超過 5～6 人就要接第三方語音伺服器（如 LiveKit），有費用與維運成本；Discord 免費且大家已經在用。不和 Discord 做任何串接（不需要 bot）。
- **暱稱對應**：大廳提示「請使用和 Discord 相同的暱稱」，讓大家能把語音中的人對到圓桌座位。
- **推送方式**：聊天訊息用增量事件 `ct:chat-message` 推給有權看的人，不每則都重推整份 `ct:state`。

#### 三種頻道

| 頻道 | 誰能看內容 | 誰能看到「存在」 | 開放時間 | 終局 |
|---|---|---|---|---|
| **公開文字**（輔助，主要討論在 Discord） | 所有人（含觀戰者） | — | 白天（`dawn` 只有系統公告） | 保留 |
| **私聊群組** | 群組成員 | **所有人**（圓桌連線），說書人看得到成員名單 | 只有 `free` 小階段能送；其他時間可閱讀 | **公開全部內容** |
| **私訊說書人** | 該玩家 + 說書人 | 只有說書人 | 任何時候（含夜晚） | 不公開 |

#### 私聊群組規則（支援 2 人以上）

- 開群組：點一位或多位玩家頭像 →「私聊」→ 被邀請者收到邀請，按「加入」才算進入（可拒絕）。邀請 30 秒沒回應自動過期。
- 群組在**第一位被邀請者接受時**才成立（開始畫線）；在那之前只有邀請，不畫線。
- 已在其他群組的人接受新邀請 → **自動離開原群組**再加入新的（邀請彈窗會先提示「接受將離開目前的私聊」）。
- 群組內的成員可以再邀請其他人；任何成員可以隨時「離開」。
- 群組人數最少 2 人；剩 1 人時自動結束。
- 每位玩家**同時只能在一個私聊群組裡**。這模擬實體遊戲「走到旁邊講話」，也讓圓桌連線保持清楚。
- 人數上限：預設不限，說書人可在設定中限制（例如最多 4 人）。
- 說書人不能加入玩家的私聊群組（只用私訊說書人溝通）。
- 「自由時間」結束（說書人按「集合提名」）時，所有群組自動解散；歷史內容保留，成員可繼續閱讀。

#### 圓桌上的私聊連線

所有人都看得到「誰跟誰在私聊」（不含內容），用四種方式呈現：

**1. 圓桌連線（即時）**

- 群組成立後，成員座位之間畫出同色連線（2 人是一條線，3 人以上連成一圈），每個群組一種顏色。
- 成員離開 → 連線即時更新；群組結束 → 連線消失。
- **自己所在的群組**：線加粗並帶流動動畫；別人的群組用細線，避免和自己的混在一起。

**2. 「私聊中」清單（避免連線太亂）**

- 圓桌旁（桌機在圓桌下方，手機在圓桌分頁頂端）列出目前所有群組，一組一列，例如：
  - 🟦 小明・小美（3 分鐘）
  - 🟧 阿華・胖虎・小夫（1 分鐘）
- 點某一列 → 只高亮該群組的連線，其他連線變淡；再點一次取消。
- 群組多時（例如 15 人局同時 4～5 組），玩家看清單比看交叉的線容易。

**3. 玩家選單（取代「滑過顯示」，手機也能用）**

- 點任一座位 → 打開玩家選單，第一行顯示狀態：「💬 正在和 小美、靜香 私聊」或「目前沒有私聊」。
- 選單下方才是操作：「邀請私聊」「提名」（提名階段）「查看今日私聊紀錄」。
- 這樣「點座位」只有一種行為（打開選單），不會和私聊、提名的點擊互相衝突。
- 座位旁仍保留小圖示 💬，一眼看出誰正在私聊；桌機滑過時顯示同樣的狀態文字作為捷徑。

**4. 私聊紀錄（回顧，推理線索）**

- 公開日誌記錄每次私聊：「09:12–09:15 小明 ↔ 小美」。
- 另有「私聊統計」表：誰跟誰聊過幾次、累計多久，可切換「今天 / 第 N 天 / 全部」。
  ```
            小明  小美  阿華  胖虎
  小明       —   3次   1次    —
  小美      3次   —     —    1次
  阿華      1次   —     —    2次
  ```
- 點表格中的格子 → 列出這兩人每次私聊的時間。
- 資料來源是 `chat.whispers[*].memberLog`：兩人「加入～離開」時間有重疊才算一次私聊，重疊長度就是時長。不需要額外儲存。

**說書人**：另有「私聊總覽」，和玩家看到的清單相同，但多顯示每個群組的邀請與加入 / 離開時間（仍看不到內容，終局才看得到）。

#### 角色標籤（加快打字聲稱）

- 聊天輸入框旁有「🎭」按鈕，打開本劇本角色清單，點一下插入角色標籤，例如 `[[role:empath]]`。
- 訊息顯示時，標籤用 `RoleToken.vue` 渲染成小圖示 + 名稱（圖示一樣來自 `assets.js`，換圖時聊天裡的標籤也會跟著換）。
- 也可以插入玩家標籤 `[[seat:3]]`，顯示為該座位的名字。

#### 限制

- 每則最多 300 字；每人每 1.5 秒最多送 1 則（防洗版）。
- 記憶體上限：公開聊天保留最近 1000 則、每個私聊群組保留 500 則。
- 不能傳圖片、連結會顯示成純文字（避免玩家用截圖證明角色；官方規則禁止出示角色牌）。

#### 介面配置

- **桌機**：中間圓桌，右側聊天側欄，分頁為「公開」「私聊（群組分頁）」「說書人」，未讀數字標在分頁上。
- **手機**：底部分頁列切換「圓桌」「公開」「私聊」「說書人」；收到私聊邀請、提名、喚醒時以浮動提示通知。
- 說書人面板：私訊分頁依玩家排列；另有「私聊總覽」只顯示所有群組的成員與時間。

## 9. 分期規劃

| 階段 | 內容 |
|---|---|
| **Phase 1：線上魔典 + 聊天（MVP）** | 見下方「Phase 1 範圍」清單。 |
| **Phase 2：說書人輔助** | 所有 `info-*` prompt **預填真實答案**與假資訊標示、說書人平衡指標、夜晚資訊隨機延遲、時間軸回放（逐步播放日誌）、私聊統計表 `WhisperStats`。 |
| **Phase 3：擴充** | 黯月初升、夢殞春宵、匯入自訂劇本 JSON、旅行者、傳奇角色（Fabled）。 |
| **Phase 4：網頁語音（可選）** | 若之後想脫離 Discord，再評估網頁內建語音（需接第三方語音伺服器如 LiveKit，有費用）。 |
| **Phase 4：自動說書人（可選）** | 只支援暗流湧動；能力自動結算；醉酒 / 中毒假資訊用規則產生（例如「給一個看起來合理但錯誤的答案」）；不需要說書人也能玩。實作量最大，建議等前面穩定再評估。 |

### Phase 1 範圍（實作時以這份為準）

**要做：**

- 房間：大廳頁、建房 / 加入、指定 / 隨機說書人、入座 / 調座位、觀戰、重連、說書人斷線暫停、玩家離開標示（第 3 節）。
- 開局：暗流湧動劇本、依人數的配置表與**合法性檢查**（含男爵、酒鬼）、隨機配置、隨機分配 + 說書人修改、惡魔偽裝、發角色（第 6 節）。
- 夜晚：**所有玩家統一的入夜畫面**、夜晚順序清單、首夜邪惡互認（7 人以上）、`choose-player` 與 `custom` 兩種 prompt、`info-*` prompt 的**介面**（說書人手動填答案，不預填）、自動提醒標記、說書人確認死亡（第 7.1～7.3 節）。
- 白天：三個小階段與計時、提名、時鐘指針投票、處決、勝負判定（第 7.4、7.5 節）。
- 聊天：公開文字、私聊群組（邀請 / 接受 / 離開 / 自動離開原群組）、圓桌連線 + 「私聊中」清單 + 玩家選單、私聊紀錄寫進日誌、私訊說書人、角色標籤、限制與防洗版（第 7.6 節）。
- 終局：全部角色公開、完整魔典、日誌列表（含說書人所有修改、假資訊）、私聊群組內容公開、計分。
- 圖片：`assets.js` + `RoleToken.vue` + `GameIcon.vue`，全部用 emoji（第 4 節）。
- 測試：`gameLogic.test.js` 與整合測試（第 10 節）。

**不做（之後的 Phase）：** `info-*` 真實答案預填、平衡指標、隨機延遲、時間軸回放動畫、私聊統計表、黯月初升 / 夢殞春宵、自訂劇本匯入、旅行者、傳奇角色、網頁語音、自動說書人。

### Phase 2 實作備註（2026-10-16）

- **真實答案預填**：`gameLogic.computeTruth(game, seat, roleId, reply)` 依魔典計算洗衣婦 / 圖書管理員 / 調查員（真角色 + 隨機另一人）、廚師、共情者（跳過死亡鄰座）、占卜師（含紅鯡魚標記）、送葬者（今天被處決者）、守鴉人。「隨機另一人」用以 `gameNo:dayNumber:roleId:seat` 為種子的亂數，重推時不跳動。隱士 / 間諜在相關位置時附上「可能被當作…」提示。說書人視圖的 `grimoire.nightQueue[].truth` 帶這份答案；夜晚順序有「照實送出」（一鍵送出 + 打勾）與「修改後送出」（`InfoComposer` 預填，改成不符時即時顯示「⚠ 給假資訊」）。
- **真假判定在伺服器**：`sendInfo` 以 `judgeInfo` 判定是否與魔典相符，寫進日誌 `isTrue`（說書人無法自稱為真；只有自訂文字等無法判定時才採用說書人的標記），並記錄對象當時是否中毒 / 醉酒（`impaired`）。前端 `data/truth.js` 的 `judgeDraft` 只是編輯時的即時預覽。
- **夜晚隨機延遲**：`wake` / `sendInfo` 帶 `delayMs`（index.js 在夜晚用 `randomDelay()` 0～1500ms），prompt / 訊息帶 `visibleAt`，`buildView` 在時間到之前不放進玩家本人的視圖；到期時只重推給該玩家（`pushStateTo`），其他人的畫面不動。
- **平衡指標**：`balanceStats(game)` → `grimoire.balance`（善惡存活比、惡魔被提名次數 / 最高得票相對門檻、粗估剩餘天數、假資訊數量、提示文字），顯示在魔典分頁頂端 `BalancePanel.vue`。
- **私聊統計**：所有人的視圖新增 `whisperLog`（每個群組的成員與加入 / 離開時間，不含內容）。`data/whisperStats.js` 依重疊時間算次數與時長，`WhisperStats.vue` 在「私聊中」分頁與終局彈窗。
- **時間軸回放**：`data/replay.js` 從 `start` 日誌開始逐筆重建圓桌（死亡、處決、離開、角色變更、參與座位標籤），`ReplayTimeline.vue` 支援播放 / 暫停 / 單步 / 速度 / 拖曳 / 只看重要事件，放在終局彈窗「時間軸回放」分頁。
- 沒有新增 socket 事件；`server/room/` 未修改。

## 11. 已確認的決定（2026-10-16）

1. ✅ **每一場都必須有真人說書人**（第 1 節）。
